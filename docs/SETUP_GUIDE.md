## 1. 背景 — なぜ IssueBoard が必要か

### 1.1 GitHub Projects の課題

GitHub には **Projects**（プロジェクトボード）という公式のプロジェクト管理機能がありますが、以下の課題があり、特に非エンジニアを含むチームでの運用に適していません。

| 課題 | 詳細 |
|------|------|
| **ガントチャートがない** | GitHub Projects にはタイムライン表示（Roadmap ビュー）はあるが、Backlog のようなガントチャート（作成日〜期限のバー表示、親子ツリー、スケール切替）は提供されていない |
| **バーンダウンチャートがない** | スプリントの進捗をバーンダウンチャートで可視化する機能がなく、残課題数の推移を追えない |
| **カスタムフィールドの管理が煩雑** | Projects のカスタムフィールド（ステータス等）は Issue のラベルとは別管理であり、二重管理が発生する |
| **UI が開発者向け** | GitHub の UI は開発者を前提としており、非エンジニアのプロジェクトメンバーにとって直感的でない |
| **組織プランの制約** | Projects の一部機能（Insights 等）は有料プランが必要。無料プランでは機能が限定される |
| **複数ビューの切替が不便** | ボード・テーブル・ロードマップの切替はできるが、一覧からの詳細表示やフィルターの連携が弱い |
| **親子課題のサポートが限定的** | タスクリスト（`- [ ] #N`）は本文内の記法であり、Projects 上でのツリー表示やサマリーバーはない |

### 1.2 IssueBoard が解決すること

IssueBoard は GitHub Issues をデータソースとしつつ、GitHub Projects では不足する機能を補完する Web アプリケーションです。

| GitHub Projects の課題 | IssueBoard での解決 |
|----------------------|-------------------|
| ガントチャートがない | 日/週/月/四半期スケール、親子ツリー、親サマリーバー、期限アイコン付きのガントチャート |
| バーンダウンチャートがない | Milestone ベースのバーンダウンチャート（理想線・実績線・今日ライン） |
| カスタムフィールドの二重管理 | GitHub のラベル（description ベース分類）をそのまま使用。別途フィールドを定義する必要がない |
| UI が開発者向け | Backlog 風の直感的な UI（サイドバー、テーブル、ボード、詳細パネル） |
| 組織プランの制約 | GitHub API のみ使用するため、無料プランのリポジトリでも全機能利用可能 |
| 複数ビューの切替が不便 | 課題一覧・ボード・ガント・バーンダウンをサイドバーで即座に切替。全ビューから詳細パネルを表示可能 |
| 親子課題のサポートが限定的 | タスクリスト形式を解析し、課題一覧のツリー表示、ガントの親サマリーバー、ボードの進捗バーを提供 |

### 1.3 IssueBoard の位置づけ

```
GitHub Issues（データソース）
  │
  ├── GitHub Projects（GitHub 公式 UI）
  │     └ ボード / テーブル / ロードマップ
  │
  └── IssueBoard（本アプリ）
        └ 課題一覧 / ボード / ガントチャート / バーンダウンチャート / 設定
```

- **GitHub Issues はそのまま使い続ける** — IssueBoard は GitHub Issues のデータを読み書きするだけで、独自のデータベースは持たない
- **GitHub Projects と併用可能** — IssueBoard を使っても GitHub Projects の機能は影響を受けない
- **既存の運用を壊さない** — ラベルの description に分類キーワードを追加するだけで導入でき、既存の Issue やワークフローを変更する必要がない

## 2. 概要

IssueBoard は GitHub Issues をデータソースとして動作します。
本ドキュメントでは、アプリを利用する前に必要な GitHub 側の設定を説明します。

### アプリの画面構成

| メニュー | 機能 |
|---------|------|
| **ダッシュボード** | 総課題数・期限超過・間近の課題・ステータス別/担当者別集計・マイルストーン進捗 |
| 課題 | Issue のテーブル一覧（ツリー表示、フィルター、ソート、詳細パネル） |
| ボード | ステータス/優先度別のカンバンボード（D&D でラベル変更） |
| ガントチャート | 日/週/月/四半期スケール、親子ツリー、グルーピング |
| **カレンダー** | 月表示で期限日ごとに Issue を表示 |
| バーンダウン | Milestone ベースのバーンダウンチャート |
| **更新履歴** | Issue の変更履歴（ラベル変更・クローズ・担当者変更等）をタイムライン表示 |
| 設定 | ステータス・優先度・カテゴリラベル、マイルストーンの作成・編集・削除 |

### 設定が必要な項目

| # | 項目 | 必須 | 備考 |
|---|------|------|------|
| 1 | リポジトリ | ○ | Issue を管理する対象のリポジトリ |
| 2 | アクセストークン | ○ | アプリから GitHub API にアクセスするための認証情報 |
| 3 | 環境変数 | ○ | アプリにリポジトリ情報を設定 |
| 4 | ラベル | ○ | 優先度・ステータス・カテゴリの分類用ラベル（**アプリの設定画面からも作成可能**） |
| 5 | マイルストーン | 任意 | バーンダウンチャート用（**アプリの設定画面からも作成可能**） |

## 3. リポジトリの準備

IssueBoard は 1 つの GitHub リポジトリの Issues を管理対象とします。
既存のリポジトリを使用するか、新規にリポジトリを作成してください。

- パブリック / プライベートどちらでも利用可能
- 組織リポジトリの場合、アクセストークンにリポジトリへの権限が必要

## 4. アクセストークンの発行

### 4.1 Classic Token（推奨）

組織リポジトリで Fine-grained Token の承認が必要な場合は Classic Token が簡単です。

1. GitHub にログイン
2. **Settings** → **Developer settings** → **Personal access tokens** → **Tokens (classic)**
3. **Generate new token (classic)** をクリック
4. 以下を設定:
   - **Note**: 任意の名前（例: `IssueBoard`）
   - **Expiration**: 任意の期限
   - **Scopes**: `repo` にチェック
5. **Generate token** でトークンを生成
6. 表示されたトークン（`ghp_` で始まる文字列）をコピーして安全に保管

### 4.2 Fine-grained Token

より細かい権限制御が必要な場合はこちらを使用します。

1. GitHub にログイン
2. **Settings** → **Developer settings** → **Personal access tokens** → **Fine-grained tokens**
3. **Generate new token** をクリック
4. 以下を設定:
   - **Token name**: 任意の名前
   - **Expiration**: 任意の期限
   - **Resource owner**: リポジトリの所有者（個人 or 組織）
   - **Repository access**: 「Only select repositories」→ 対象リポジトリを選択
   - **Permissions** → **Repository permissions**:
     - **Issues**: Read and write
5. **Generate token** でトークンを生成

> **注意**: 組織リポジトリの場合、Fine-grained Token は組織管理者の承認が必要です（ステータスが Pending になります）。承認されるまでトークンは使用できません。

### 4.3 トークンに必要な権限

| 操作 | 必要な権限 |
|------|-----------|
| Issue の閲覧 | Issues: Read |
| Issue の作成・クローズ | Issues: Write |
| ラベルの作成・変更・削除 | Issues: Write |
| マイルストーンの作成・変更・削除 | Issues: Write |
| コメントの追加 | Issues: Write |

> **補足**: トークンはブラウザの `sessionStorage` に保存されます。**タブを閉じると自動的に削除される**ため、再度アクセスする際はトークンの再入力が必要です。トークンの文字列は手元に保管しておいてください。

## 5. 環境変数の設定

アプリのルートディレクトリにある `.env` ファイルを編集します。

```env
VITE_REPO_OWNER=リポジトリの所有者名
VITE_REPO_NAME=リポジトリ名
```

**設定例**:

```env
VITE_REPO_OWNER=haruki-kubo
VITE_REPO_NAME=todo
```

> URL が `https://github.com/haruki-kubo/todo` の場合、`VITE_REPO_OWNER=haruki-kubo`、`VITE_REPO_NAME=todo` となります。

### 5.1 E2E テスト用の環境変数

Playwright による E2E テストを実行する場合は、通常の `.env` とは別に実行時環境変数 `E2E_GITHUB_TOKEN` が必要です。

| 変数名 | 必須 | 説明 |
|--------|------|------|
| `E2E_GITHUB_TOKEN` | ○ | E2E テスト用の GitHub Personal Access Token |
| `E2E_REPO_OWNER` | 任意 | テスト対象のリポジトリオーナー名。省略時は `haruki-kubo` |
| `E2E_REPO_NAME` | 任意 | テスト対象のリポジトリ名。省略時は `todo` |

**実行例**:

```bash
E2E_GITHUB_TOKEN=ghp_xxx \
E2E_REPO_OWNER=haruki-kubo \
E2E_REPO_NAME=todo \
npm run test:e2e
```

## 6. ラベルの設定

ラベルは **アプリの設定画面** または **GitHub 上** のどちらからでも設定できます。

### 6.1 アプリの設定画面から設定（推奨）

1. アプリにログイン後、サイドバーの **「設定」** を開く
2. **ステータス / 優先度 / カテゴリ** のタブを選択
3. **「+ 新規作成」** で名前・色・順序（ステータス/優先度のみ）を入力して作成

アプリが description を自動設定するため、GitHub 上での手動設定は不要です。

### 6.2 GitHub 上で設定

GitHub リポジトリの **Settings** → **Labels** で直接設定する場合は、各ラベルの Description に分類キーワードを設定してください。

#### 分類ルール

| Description に含める文字列 | 分類 | 用途 |
|--------------------------|------|------|
| `priority` または `priority:N` | 優先度 | 課題の緊急度を表す |
| `status` または `status:N` | ステータス | 課題の進捗状態を表す |
| `category` | カテゴリ | 課題の分野・部門を表す |

- `N` は表示順序を指定する数値（1 が先頭、小さいほど左に表示）
- `N` を省略した場合は GitHub API の返却順で表示
- カテゴリには順序指定はありません（`category` のみ）
- 上記いずれにも該当しないラベルは分類対象外

#### 推奨ラベル構成

**優先度ラベル**:

| ラベル名 | Description | 色 |
|---------|-------------|-----|
| 🔴 緊急 | `priority:1` | `#d73a4a` |
| 🟡 今週 | `priority:2` | `#fbca04` |
| 🔵 次週以降 | `priority:3` | `#0075ca` |
| 👀 確認待ち | `priority:4` | `#f9d0c4` |

**ステータスラベル**:

| ラベル名 | Description | 色 |
|---------|-------------|-----|
| 未対応 | `status:1` | `#9ca3af` |
| 処理中 | `status:2` | `#6366f1` |
| 処理済み | `status:3` | `#22c55e` |

**カテゴリラベル**:

| ラベル名 | Description | 色 |
|---------|-------------|-----|
| 🏢 経理総務 | `category` | `#0e8a16` |
| 👥 採用労務 | `category` | `#d876e3` |
| 🔒 情シス | `category` | `#006b75` |

### 6.3 注意事項

- Description を設定しないラベルは IssueBoard の分類対象外になります
- 1 つの Issue に対して、各分類（優先度・ステータス・カテゴリ）から最大 1 つずつ付与してください
- ラベル名は自由に変更できます（Description の内容で分類されるため）
- ラベルの色はアプリ内でそのまま表示に使用されます

## 7. マイルストーンの設定（バーンダウンチャート用）

マイルストーンも **アプリの設定画面** または **GitHub 上** のどちらからでも設定できます。

### 7.1 アプリの設定画面から設定（推奨）

1. アプリにログイン後、サイドバーの **「設定」** を開く
2. **マイルストーン** タブを選択
3. **「+ 新規作成」** でタイトル・期限日・説明を入力して作成
4. 説明欄に `開始日: YYYY-MM-DD` を記載すると、バーンダウンチャートの開始日として使用されます

### 7.2 GitHub 上で設定

1. GitHub リポジトリの **Issues** → **Milestones** を開く
2. **New milestone** をクリック
3. 以下を設定:
   - **Title**: スプリント名やリリース名（例: `Sprint 1`、`v1.0`）
   - **Due date**: 期限日（バーンダウンチャートの終了日になる）
   - **Description**: 任意
     - 開始日を明示したい場合は `開始日: YYYY-MM-DD` または `開始日: YYYY/MM/DD` を記載
4. **Create milestone** で作成

### 7.3 Issue をマイルストーンに紐づけ

- Issue の作成時または編集時に **Milestone** を選択
- 複数の Issue を同じ Milestone に紐づけることで、バーンダウンチャートに反映される

### 7.4 バーンダウンチャートの見方

- **理想線**（グレー破線）: 期間内に均等に消化した場合のライン
- **実績線**（青実線）: 実際の残課題数の推移
- 実績線が理想線の下にあれば順調、上にあれば遅延

## 8. Issue の作成ルール

### 8.1 開始日・期限の設定

Issue の本文に以下の形式で記載すると、アプリ上で開始日・期限として認識されます。

```
📅 開始日: 2026-04-01
📅 期限: 2026-04-15
```

- `YYYY-MM-DD` または `YYYY/MM/DD` 形式に対応
- アプリの新規作成モーダルや詳細パネルから設定した場合、本文に自動挿入されます
- **開始日** はガントチャートのバー開始位置に使用されます。未指定時は Issue の起票日が使用されます
- **期限** は課題一覧・ボード・ガントチャートの期限表示に使用されます

### 8.2 担当者の設定

GitHub Issues の **Assignees** で担当者を設定すると、アプリ上で担当者が表示されます。

- 課題一覧: 担当者列にアバターとユーザー名
- ボード: カード内にアバター
- ガントチャート: 左列にアバター
- フィルター: 担当者で絞り込み可能

### 8.3 親子課題（サブタスク）

課題に親子関係を持たせることができます。

**方法 1: アプリから作成（推奨）**

新規課題作成モーダルで「親課題」を選択するだけで、自動的に親子関係が構築されます。

**方法 2: GitHub 上で手動設定**

親 Issue の本文にタスクリスト形式で子 Issue の番号を記載します。

```markdown
### サブタスク
- [ ] #2
- [ ] #3
- [ ] #4
```

- 子 Issue を Close すると、GitHub が自動的に `- [x] #N` に更新します
- 子 Issue 側には特別な記法は不要です
- アプリは全 Issue（Open + Closed）の本文を走査して親子関係を自動認識します

**アプリ上での表示**:

| 画面 | 表示内容 |
|------|---------|
| 課題一覧 | 親 Issue の下に子 Issue をインデント表示。展開/折りたたみ可能 |
| 詳細パネル | 親課題リンク、サブタスク一覧、進捗バー |
| ボード | 親 Issue のカードにサブタスク進捗バー |
| ガントチャート | 「親課題」でグルーピング可能。親サマリーバー表示 |

## 10. セキュリティに関する注意事項

### 10.1 PAT の保管

| 項目 | 内容 |
|------|------|
| 保管場所 | ブラウザの `sessionStorage`（平文、タブを閉じると自動削除） |
| リスク | XSS 攻撃や悪性ブラウザ拡張機能が存在する場合、セッション中に PAT が抜き取られる可能性がある |
| 影響範囲 | PAT に `repo` スコープがある場合、リポジトリへの書き込み権限が奪われる |
| 軽減策 | `sessionStorage` を使用しているため、タブを閉じればトークンは自動的に消去される。共有 PC での放置リスクを排除 |

**推奨対策**:
- PAT の有効期限をできるだけ短く設定する（例: 30 日）
- Fine-grained token を使用し、対象リポジトリと権限を最小限にする
- 信頼できないブラウザ拡張機能をインストールしない
- 使用後はタブを閉じる（`sessionStorage` からトークンが自動削除される）
- 定期的にトークンをローテーションする

### 10.2 トークン検証

ログイン時のトークン検証では、以下の 3 段階で検証を行います:

1. **ユーザー認証** — `GET /user` でトークン自体の有効性を確認
2. **リポジトリアクセス** — `GET /repos/{owner}/{repo}` で対象リポジトリへのアクセス権を確認
3. **書き込み権限** — ラベル作成（POST）を試行し、書き込み権限があるか確認（テストラベルは即削除）

権限不足や読み取り専用のトークンではログインできず、エラーメッセージで原因を案内します。

### 10.3 アーキテクチャ上の制約

IssueBoard はサーバーを持たない静的 SPA であり、ブラウザから GitHub API を直接呼び出す構成です。

| 項目 | 制約 |
|------|------|
| 秘密管理 | サーバー側でトークンを管理できないため、ブラウザ内に保持する |
| 監査ログ | アプリ独自の監査ログはなし。GitHub 側の Audit log に依存 |
| CSP | GitHub Pages のデフォルト CSP に依存 |

### 10.4 更新履歴の表示範囲

更新履歴（Activity Feed）は GitHub API の最新 300 件（3 ページ分）のイベントのみを表示します。完全な監査ログではなく、**直近の変更を確認するための参考情報**です。

- イベントが大量に発生した場合、古いイベントは表示範囲外になります
- 監査目的には GitHub の Audit log（組織プラン）または API の直接参照を使用してください

## 11. トラブルシューティング

| 症状 | 原因 | 対処法 |
|------|------|--------|
| 404 エラー | リポジトリにアクセスできない | `.env` のオーナー名・リポジトリ名を確認。トークンの権限・有効期限を確認 |
| ラベルがフィルターに表示されない | Description が未設定 | アプリの設定画面からラベルを作成するか、GitHub のラベル設定で Description に `priority` / `status` / `category` を含めているか確認 |
| ステータスの列順が意図と異なる | `status:N` が未設定 | アプリの設定画面で順序番号を設定するか、ラベルの Description を `status:1`、`status:2` のように順序付きに変更 |
| 設定画面でラベル作成が失敗する | トークンの権限不足 | `Issues: Read and write` 権限（Fine-grained）または `repo` スコープ（Classic）が必要 |
| Fine-grained Token が使えない | 組織の承認待ち | 組織管理者に承認を依頼するか、Classic Token を使用 |
| Issue が表示されない | PR が混在 / Issue が Closed | IssueBoard は Open な Issue のみ表示。Pull Request は自動除外 |
| マイルストーンが表示されない | マイルストーン未作成 | アプリの設定画面またはGitHub の Issues → Milestones から作成 |
